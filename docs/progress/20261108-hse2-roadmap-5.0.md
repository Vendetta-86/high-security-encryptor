# HSE2 Roadmap 5.0

> **实施要求：**严格按阶段和验收条件推进。此路线图不自动改变容器默认格式、不承诺稳定版、不扩大安全声明，也不触发发布；每一项都以仓库内可复跑证据验收。

**目标：**在 v0.8.3 与路线图 4.0 完成的基础上，补齐 HSE2 v5 的完整归档兼容基线、关键工作流的 Windows 打包覆盖与跨版本回归，然后依据这些证据决定 v5 是否继续保持实验性。

**路线图版本：**5.0。它是开发范围和验收顺序，不代表产品版本或发布日期。

**制定日期：**2026-11-08。

## 基线

- 最新产品版本为 v0.8.3。精确标签 Windows Actions run `42474370890` 的构建、下载包校验和公开发布作业成功；公开 ZIP 独立下载后 SHA-256 与 Release API digest 一致，117 个文件完整提取，10 个 EXE 存在，CLI 与两个 GUI 的启动冒烟通过。
- 路线图 4.0 阶段 0–5 已完成，结项记录见 [路线图 4.0](20261107-hse2-roadmap-4.0.md)。BitLocker 状态门禁、恢复信息失败与重试、用户教程走查和公开资产验收均已闭环；实体设备证据限于路线图 4.0 所记录的设备和场景。
- 路线图制定时（2026-11-08）本地全量回归为 802 项通过、6 项跳过，v5 定向回归为 42 项通过。阶段 1 完成后（2026-11-09）全量回归为 804 项通过、6 项跳过，v5 定向回归为 44 项通过；全仓 detect-secrets hook 通过。发布与成熟度基线见 [v0.8.3 公开资产复核](20261108-hse2-roadmap-4.0-public-release-v0.8.3-check.md) 和 [v5 成熟度决策](20261108-hse2-v5-maturity-decision.md)。
- 现有固定完整容器夹具有 HSE2 v2 和 v3；v4/v5 有 codec、workflow、边界与错误路径测试，但当前没有完整冻结的 v4/v5 二进制归档夹具。v5 固定字节夹具目前只有 public header 和 footer。
- Windows Release 工作流现已对打包版 v5 执行 create、verify 和 restore 往返；CLI 已提供 v5 preview、password update、replace、compact 和 v4-to-v5 等命令，v5 GUI 也有对应操作表单。其余维护命令尚未在打包 EXE 中做完整端到端往返验收。
- 当前 GitHub 仓库没有开放 issue。没有第三方认证或独立外部审查作为门槛；这是自用项目，路线图按本地格式、兼容性、故障处理和发布证据验收。

**路线图状态：**阶段 0–2 已完成；阶段 3–5 尚未开始。

## 目标与原则

1. 给 v5 增加可长期保存、跨提交读取的完整归档基准，减少 wire format 漂移风险。
2. 确认 v5 的 create/open/verify/preview/password update/replace/compact/v4 export 在源码和 Windows 发布包之间行为一致。
3. 保持 v2/v3/v4 历史容器可读；新版本不静默迁移旧容器。
4. 只有完成本地兼容性和发布验收后才重新审议 v5 标签；测试通过不等于密码学认证。
5. 不把默认创建格式从 v2 改成 v5。任何默认值或支持策略变化都要另立决策记录。

## 关键验收门槛

### 完整格式夹具

- 归档必须是完整的可读 v5 容器，而不是单独 header/footer 或某一个 codec 向量。
- 测试记录 fixture 如何产生、包含哪些测试专用密钥/口令，以及如何验证恢复内容；fixture 不得包含用户数据。
- 生产代码继续使用系统安全随机源。确定性测试能力不得作为用户可设置的运行选项暴露。
- 旧格式夹具的字节、读取结果和默认创建版本必须保持一致；失败时停止稳定化评估，先定位版本分派或兼容性回归。

### 生命周期与失败处理

- 更新、迁移和压缩写入独立目标；成功前源文件保持不变。
- 明确测试“目标已存在”“空间不足”“错误口令”“描述符/记录认证失败”“flush/replace 失败”和暂存目录清理。
- 单视图更新不得要求访问对侧口令，也不得丢失对侧活动视图；需要双口令的操作必须在 UI 和 CLI 明示。
- 对容器长度、活动 chunk、条目数、路径长度、描述符大小和 JSON 深度继续执行有界检查；不因实现 fixture 而放宽格式限制。
- 不声称支持掉电持久性、回滚抵抗、安全擦除或隐藏元数据，除非另有实现和独立的验收证据。

### Windows 发布资产

- exact-tag 工作流必须使用标签对应源码，并验证打包 EXE 的成功与预期失败路径。
- 公开 ZIP 必须独立下载，核对 Release API SHA-256、解压清单、版本标识、教程和可执行入口。
- 将源码 commit、tag、workflow run、asset 名称与摘要关联到一份发布验收记录。
- 用户密码、恢复密钥、keyfile 内容不得写入 workflow 日志、命令行参数、公开报告或发布资产。

## v5 成熟度复审规则

阶段 5 必须输出一个明确状态，不可将所有测试通过直接等同于稳定：

- 如果完整冻结夹具、旧格式回归、打包维护工作流或发布证据任一缺失，v5 继续标记为实验性，并列出具体缺项。
- 如果上述本地可复跑门槛全部通过，可将 v5 提交为“稳定候选”供项目维护者决定；这仍不代表密码学认证、普遍安全保证或强制切换默认格式。
- 第三方认证和独立外部审查不属于本路线图门槛。是否提升标签只依据记录的本地实现与兼容证据。
- v5 公开承诺仍限于明确披露的双视图备用内容，不包含可否认性、胁迫安全、反取证或安全擦除。

## 不纳入 5.0

- 真正可否认性、隐藏卷、胁迫口令、自动毁坏数据或反取证。
- HSE2 v6、新 wire format、默认创建格式切换或对现有容器静默迁移。
- 云同步、账号/远程密钥托管、移动端、虚拟磁盘或文件系统驱动。
- 为增加功能数量而重做已通过教程走查的入门流程，或重开路线图 4.0 已通过的 BitLocker 状态门禁工作。
- 第三方认证、独立外部审核或密码学安全证明。
- 没有复现依据的性能改写、复杂自动修复和超出已声明格式界限的保证。

## 风险

| 风险 | 控制 |
|---|---|
| 固定随机材料意外进入生产路径 | 固定随机源仅用于测试注入；测试确认生产路径不接受测试开关或环境变量。 |
| 新夹具与新 writer 同时改变，掩盖读取兼容缺陷 | fixture 一旦提交即冻结；兼容测试始终从已保存的 fixture 读取，不在测试运行时重新生成 expected archive。 |
| CLI 通过但打包 EXE 或 GUI 参数映射错误 | 发布 workflow 执行实际归档往返；GUI 手工验收与 CLI 测试分别记录，不相互替代。 |
| 将本地验收误读成全面密码学保证 | 发布说明列出验证范围和非目标；v5 标签决策独立记录，不自动改变默认格式。 |

## 结项规则

只有阶段 1–5 均完成、完整 v5 夹具与旧格式回归通过、打包版维护工作流成功、公开资产复核完成且 v5 成熟度结论已记录后，才可以宣告路线图 5.0 完成。若 v5 门槛不满足，路线图仍可按“v5 保持实验性、缺口明确披露”结项，但不得宣称 v5 已稳定；结项不批准默认格式变化。
