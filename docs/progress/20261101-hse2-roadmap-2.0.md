# HSE2 Roadmap 2.0

**状态：阶段 0 已完成；阶段 1 源码工作完成（Windows ZIP 验收留待 v0.8）；阶段 2 设计完成；阶段 3 已完成；阶段 4 进行中**

**基线日期：2026-11-01**
**承接：路线图 1.0 已完成**

路线图 2.0 把重点从“补齐 HSE2 的主要功能”转到“让已发布的功能更实用、更可靠、更容易使用”。这里的 2.0 是路线图版本，不是产品版本。本文依据当前仓库、已发布的 v0.7.0、现有测试记录和 GitHub backlog 编写；未经本地复测的测试数字以最近记录为准。

## 1. 现状基线

- 路线图 1.0 的计划范围已完成。HSE2 v2/v3、wrapper/KDF/keyfile/DPAPI、CLI、实验 GUI、Windows 打包与发布流程均已有实现；HSE2 v4 双视图备用内容已随 `v0.7.0` 发布。
- v4 是公开的双视图格式：两组口令分别打开各自内容。它不承诺可否认性、抗取证、抗胁迫或主机痕迹保护，也不修改 v2/v3。
- v4 的固定布局带来明显的小文件成本：最小容量容器大小为 `170 + 2 × 67,108,864 + 2 × 1,048,576 = 136,315,050` 字节，约 130 MiB。两个固定描述符区域占 128 MiB；即使内容很少，容器也无法小很多。
- v4 GUI 每个视图每次操作只接受一个文件映射；CLI 支持重复映射。CLI 文档中的 Windows Release ZIP 状态已按 v0.7.0 验收证据修正。
- 阶段 0 开始时，文档记录全量测试为 714 项通过、6 项跳过；阶段 1 本机回归为 722 项通过、6 项跳过；加入 v5 codec 层后为 729 项通过、6 项跳过；文件 I/O/CLI 后为 739 项通过、6 项跳过；GUI 接入后为 744 项通过、6 项跳过；wire fixtures/故障注入后为 749 项通过、6 项跳过；原子写入测试后为 752 项通过、6 项跳过；有界 malformed-input fuzz 后为 753 项通过、6 项跳过；恢复崩溃清理租约后为 756 项通过、6 项跳过；ENOSPC 刷盘失败测试后为 757 项通过、6 项跳过；v5 record/manifest 往返覆盖后为 759 项通过、6 项跳过；加入 Windows 临时 sharing violation 重试后，当前全量回归为 **760 项通过、6 项跳过**（2026-11-01）。v5 三轮本机性能基线见 [`20261101-hse2-v5-baseline.md`](20261101-hse2-v5-baseline.md)。Windows CI 覆盖 Python 3.11、3.12、3.13；v0.7.0 Windows 发布工作流完成十个 EXE 检查和打包 v4 smoke。
- v4 更新写到新目标并保留源文件；格式记录指出 `os.replace` 不代表断电持久性，除非启用 `HSE_FSYNC=1`。所有写入边界的断电恢复尚未证明。
- 阶段 0 已整理 GitHub backlog：[#35](https://github.com/Vendetta-86/high-security-encryptor/issues/35) 按完成关闭；[#41](https://github.com/Vendetta-86/high-security-encryptor/issues/41) 按核心范围完成关闭；重复项 [#39](https://github.com/Vendetta-86/high-security-encryptor/issues/39) 已关闭并指向 #41。

## 2. 2.0 目标

1. 保留 v2/v3/v4 读取能力，任何不兼容的容器布局变更都使用新格式版本，并提供显式导出迁移。
2. 消除 v4 固定 128 MiB 描述符开销对小型备用内容容器造成的实用性障碍。
3. 明确文件更新、恢复和异常中断时的持久性保证；让用户能区分“原子替换”与“断电后可恢复”。
4. 降低 Windows 桌面用户的首次使用成本，并让 CLI 和 GUI 对同一功能的能力差距可见、可控。
5. 维持已验证的密码处理、认证失败、明文暂存和旧格式兼容边界，不以功能数量换取安全性。

## 4. 性能与存储验收目标（阶段 2 冻结的实现目标）

先测量 v4 的空容器、单视图 1 字节、双视图各 1 字节、1 MiB、64 MiB、多小文件和接近容量上限场景，记录输出体积、创建/替换时间、峰值内存和失败清理结果。

v5 的首版目标以 v4 基线和 1 MiB 记录上限为依据，阶段 3/5 必须实测；若需调整目标，先更新设计与理由：

- 空双视图容器不再因描述符预留达到百 MiB；目标上限建议为 1 MiB。
- 每个小文件只支付实际分配记录和紧凑 manifest 的成本；1 字节单视图容器目标不超过 2 MiB，双视图各 1 字节目标不超过 3 MiB。
- 对大文件以流式处理为主；峰值内存不随完整输入文件大小线性增长。测试报告要说明 manifest 与缓冲区的固定上限。
- 在相同机器、相同数据集上对比 v4 与 v5；报告写明容器大小、创建/替换用时和峰值内存，不能只用单次 smoke 结果宣称更快。

这些是版本规划目标，不是当前 v4 的承诺。若 v5 设计无法达到这些体积目标，应先说明安全/实现成本，再调整目标，不得静默改动已发布 v4 布局。

## 5. 明确不纳入 2.0

- 真正的 plausible deniability、隐藏卷、反取证、抗胁迫或主机系统痕迹保护；如以后研究，另建目标和版本计划。
- 输入特定口令后自动删除真实内容、wrapper 或证据。
- 虚拟磁盘/文件系统驱动、系统盘加密、云同步服务、账号体系或移动端重写。
- 宣称 SSD/操作系统缓存上的明文能够被彻底安全删除。
- 把第三方认证或独立审查设为自用项目的发布门槛。项目仍需本地测试、格式审阅和诚实披露边界。
- 在没有需求或可测收益前，把 batch rewrap、递归目录、多种 sidecar/template、自动 keyfile 轮换全部纳入主线。相关说明中的未实现条目先做需求取舍，不自动等同于承诺。

## 6. 风险和控制

| 风险 | 控制 |
|---|---|
| 为降低容器体积改格式导致旧档案不可读 | 新格式版本、向后读取回归、显式导出迁移、旧版 fixtures；不在原文件上升级 |
| 小文件优化破坏认证或记录隔离 | 先定 wire format 和不变量，再实现 codec；测试索引、长度、nonce/AAD 绑定与跨视图替换 |
| 误把“备用视图”宣传成隐藏/安全胁迫功能 | UI、CLI、README、发布说明统一使用 alternate view/备用内容；保留不承诺可否认性的警示 |
| 断电时输出看似成功但无法恢复 | 逐状态故障注入；区分原子可见性与介质持久性；不超出实测环境承诺 |
| 功能扩张拖延 v5 核心目标 | v0.8 先交付效率、耐久性和兼容；批处理/轮换等单独评估，不进入关键路径 |
