# HSE2 Roadmap 4.0

> **实施要求：**按阶段和验收门槛推进；不要因本计划而默认改变容器格式、执行真实磁盘操作或扩大产品承诺。

**目标：**以 v0.8.2 为基线，把项目从“功能和教程覆盖完成”推进到“关键操作状态可解释、恢复路径可验证、公开发布件可独立复核”。

**方法：**先固定已经观察到的使用场景，再补齐 BitLocker 状态与恢复验证、可直接照做的排障指南、发布后资产验收，最后根据兼容性证据决定 HSE2 v5 是否继续保持实验性。优先补可靠性和验收闭环，不预设新格式或大规模功能扩张。

**技术栈：**Python 3.11+、Tkinter、PowerShell/BitLocker、PyInstaller、GitHub Actions；HSE2 v2/v3/v4/v5。

**依据：**[路线图 3.0](20261102-hse2-roadmap-3.0.md)、[阶段 3 用户功能清单](20261103-hse2-roadmap-3.0-phase3-feature-inventory.md)、[v0.8.2 发布说明](../releases/v0.8.2.md)、[发布清单](../release_checklist.md)、[Windows EXE 发布说明](../windows_exe.md)。

## 全局约束

- 继续支持 Python 3.11 及以上版本；保留 v2/v3/v4 已发布档案的读取能力。
- v5 继续作为明确披露的双视图备用内容格式；不得暗示隐藏卷、可否认性、抗胁迫、反取证或安全擦除。
- 不要求第三方认证或独立外部审核；项目按自用项目执行本地审查、自动化测试和边界披露。
- 密码、恢复密钥和 keyfile 内容不得进入命令行参数、日志或公开诊断报告。
- 归档更新写入独立目标；失败、取消或空间不足时保留源档案，不发布半成品。
- 不对真实磁盘执行加密、解锁、上锁、解密或格式化，除非该次操作有明确目标、备份和用户确认。
- 不把自动化测试、单设备验证或 GitHub 提供的摘要表述成未实际执行的独立下载或跨设备验证。

## 评审重点

- BitLocker 报告加密进行中、已加密、保护关闭或状态未知时，界面和 CLI 是否给出与实际可执行动作相符的说明；不得重复启动加密。
- PowerShell 输出混有诊断信息或中文错误时，状态解析是否仍保持有效，且不会误导用户采取破坏性操作。
- 恢复信息保存、错误返回、重新插拔和恢复密码解锁各自的证据范围是否清楚；未实测不得声称通过。
- 教程代码块是否可以原样复制；不得把 `PS>`、`>>` 等交互提示符当成命令内容。
- 发布后的 ZIP 是否确实可从公开 Release 下载、摘要一致、归档可解压且入口可启动；不能只验证上传前的 workflow artifact。

## 目标

1. 明确 BitLocker 卷状态与各按钮可执行条件，验证恢复信息在失败与重试场景下仍可用。
2. 让新手能按准确的命令、预期结果和安全停止条件处理常见移动存储状态。
3. 将 Windows Release 验收从“上传前包验证”扩展为“下载公开资产后独立复核”。
4. 用可复跑的兼容性、打包和用户操作证据决定 v5 的成熟度状态；默认格式另设决策，不随路线图自动改变。

## 关键验收矩阵

### BitLocker

至少覆盖以下卷状态：完全解密、加密进行中、完全加密、解密进行中、保护开/关/未知、锁定/未锁定，以及 PowerShell 返回诊断文本或命令错误。测试验证：

- 已保护或正在转换时显示实际状态，不把它呈现为加密失败，也不重复启动加密。
- 锁定卷即使保护状态未知，也只有在系统能提供受测解锁路径时才开放解锁动作；否则给出可恢复说明。
- 恢复信息在启用加密前写入并 flush；写入失败不得启动加密；之后命令失败时保留并指出恢复文件位置。
- 文本/JSON 状态输出均有稳定结构；用户看到的摘要不会把“正在转换”混同为“100% 完成”。
- 测试报告把模拟覆盖、应用冒烟和实体设备操作分别记录，不互相替代。

### 新手指导

- 教程先用只读命令核对设备标识和状态，再说明哪些按钮会改变磁盘。
- PowerShell 代码块只含可执行命令；提示符、续行符和示例输出分别放在说明文字或输出块中。
- 每个操作都给出成功标志、失败后停止条件、恢复信息位置和下一步；不要求用户根据模糊的“失败”自行猜测。
- 操作说明覆盖 GUI 当前按钮名称与应用版本；当代码或字段变化时，有对应文档检查或回归记录。

### 发布资产

- 独立下载以公开 tag URL 为来源，不复用 Actions artifact 下载目录。
- 公开 Release API 的资产摘要必须与本地下载内容 SHA-256 相符。
- ZIP 可完整解压；关键教程、GUI/CLI 可执行文件均存在。
- CLI `--help` 和两个 GUI 的 smoke test 在干净解压目录通过；不以文件存在代替启动验证。

## 不纳入 4.0

- 真正可否认性、隐藏卷、胁迫口令、自动毁坏真实数据或系统痕迹保护。
- 外部认证、独立第三方实现或审核；按用户已作出的项目范围决策，不作为自用版本门槛。
- HSE2 v6、新的容器 wire format、默认格式切换或静默迁移。
- 云同步、账号系统、密钥托管、移动端、虚拟磁盘/文件系统驱动。
- SSD、快照、日志、备份或突然断电场景下的安全擦除/持久性保证。
- 为填满路线图而增加新算法、复杂的自动修复或没有真实需求支持的大型界面改造。

## 风险与决策门

| 风险 | 控制 |
|---|---|
| BitLocker 状态组合在不同 Windows/设备上差异导致误操作 | 先用只读状态核对和模拟状态矩阵；UI 仅呈现受支持动作；实体验证使用独立备份设备，不碰系统盘。 |
| 恢复信息写入成功但后续加密失败，引发用户误以为设备可用 | 明确报告转换状态、恢复文件位置和恢复/重试条件；发生状态不明时停止自动化重试。 |
| 教程仍然让新手复制提示符或执行错误对象 | 代码块静态检查、设备身份二次确认、预期输出示例和人工走查。 |
| Actions 包正确但公开 Release 上传内容损坏或不完整 | 发布后单独下载公开 asset，核对 API 摘要、ZIP 内容和启动入口。 |
| 把本地通过或自用经验误解为通用密码学保证 | v5 保持实验性，发布材料只陈述实际验证范围；默认格式决策独立审批并记录理由。 |

## 结项规则

路线图 4.0 只有在阶段 1–5 完成、公开资产发布后验收成功、支持范围与实际证据一致、未测场景被明确记录后才能结项。恢复密码实体设备验证若未安全执行，须保留为已知未验证边界，不得伪报通过；如果它成为 v5 或 BitLocker 新使用场景的必要条件，应另行决定是否阻塞对应功能发布。

路线图 3.0 的完成不自动批准 4.0 的实现。阶段状态和证据应随每次开发提交滚动更新；没有用户/设备需求证据的扩展功能应留在不纳入范围。
